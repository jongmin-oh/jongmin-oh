# 만들기 전에 판다 — 개발 전 검증

> **한 줄**: 빨리 만드는 능력이 있을수록, **만들기 전에** 수요를 확인하는 단계가 필요하다.
> 이건 새로 배운 방법론이 아니라 [[reflections/초기-스타트업-시행착오]]에서 **파생된 결과물**이다 — 잘 만들었는데 아무도 원하지 않았던(1번), 기능부터 붙였던(5번) 비용을 치르고 나서 순서를 뒤집었다.

---

## 명제

> **제품을 만들기 전에, 가장 싼 방법으로 먼저 팔아본다.
> 팔리는 것이 확인된 가설만 만들고, 만든 뒤에도 다음 관문을 미리 정해둔다.**

[[reflections/80퍼센트-프로토타입]]이 "만들 때 어디서 멈추는가"라면, 이 페이지는 **"만들기 시작해도 되는가"** — 80%보다 한 단계 앞, 0%에서의 판단이다.

| 단계 | 질문 | 도구 |
|---|---|---|
| 개발 전 (이 페이지) | 이걸 원하는 사람이 있는가? 어떤 말로 원하는가? | 광고·랜딩(가짜 문), 경쟁 서비스 분석 |
| 개발 중 ([[reflections/80퍼센트-프로토타입]]) | 어디까지 만들면 검증되는가? | 80% 정지선, 서버리스 |
| 개발 후 ([[reflections/코더에서-문제해결사로]] 증거 2·3) | 실제로 좋아졌는가? | 지표 정의, A/B 테스트 |

## 기원 — 시행착오에서 파생된 순서

| 시행착오 | 그때 한 것 | 뒤집은 순서 |
|---|---|---|
| 1. 완벽하게 숨겨 만들었더니 아무도 원하지 않았다 | 만든 뒤에 수요를 확인 | **수요를 먼저 확인**하고 만든다 |
| 5. 지표가 떨어지면 기능부터 추가했다 | 진단 없이 기능이라는 처방 | **판정 기준을 미리 정하고** 데이터로 결정 |
| 3. MVP인데 스코프가 부풀었다 | "있으면 좋을텐데"로 범위 확장 | 검증 결과를 근거로 **범위를 오히려 줄인다** |

그리고 [[reflections/80퍼센트-프로토타입]]의 **그림자 2번**("만드는 비용이 싸면 안 만들 결정이 더 어려워진다")에 대한 직접적인 대응이기도 하다. 빨리 만드는 사람에게 가장 강한 유혹은 "일단 만들어보자"다 — 그래서 만들기 전에 관문을 하나 둔다.

## 방식 — 개발 전 검증의 두 가지 형태

### A. 남이 검증한 수요를 빌려온다 (경쟁 서비스 분석)
[[projects/company/AI소설생성API]]: 코드를 쓰기 전에 경쟁 서비스의 기능을 태그·옵션 단위까지 뜯어 명세로 만든 뒤 착수. 시장이 이미 돈을 내고 있는 지점을 수요의 근거로 삼는 방식. 싸고 빠르지만 **"그 수요가 나에게도 오는가"는 알려주지 않는다.**

### B. 내 가설을 직접 팔아본다 (가짜 문 광고 A/B) ← 대표 사례
아래 클로이 사례. 제품 없이 광고와 랜딩 페이지만으로 **"누가, 어떤 말에 반응하는가"**를 직접 측정한다.

## 사례 — AI 영어 친구 '클로이' 기획 (2026.09, 개인)

> **상태: 기획 + 광고 검증까지만 진행. 제품 개발은 착수하지 않음.** (2026-09-29 본인 확인)

### 가설
영어 회화 학습이 지속되지 않는 진짜 이유는 커리큘럼 부족이 아니라 **매일 영어를 쓸 이유가 없어서**다. 한국어를 못하는 외국인 친구 캐릭터(호주 브리즈번, 한국계 3세)가 있으면 영어를 쓸 이유가 생긴다.
→ 이걸 **'영어 학습'으로 팔아야 하는가, '관계'로 팔아야 하는가**가 첫 번째로 검증할 질문이었다.

### 한 일 — 제품보다 광고와 랜딩을 먼저
두 가지 문구(A: 영어 학습 / B: 외국인 친구와의 관계)로 광고를 돌리고, 랜딩 페이지의 **다운로드 버튼 클릭**을 진짜 의도 지표로 **미리 지정**했다.

```
                    A안(영어)    B안(관계)
노출                  4,666       4,341
방문                     69         116
CTR                   1.48%       2.67%     B 1.8배
다운로드 클릭률          8.6%       24.8%     B 2.9배 ★ (사전 지정 지표)
사전예약 이메일             2           4
총 광고비                        $20.19
```

다운로드 클릭률 차이는 통계적으로 유의(z ≈ 3.0, p ≈ 0.002).

### 결과로 바뀐 것 — 검증이 기획을 실제로 바꿨다
1. **판매 문구 확정**: 광고·랜딩은 전부 관계 프레임. 영어는 기능이 아니라 **설정**("클로이는 한국어를 못한다")으로만 남김 → 앱스토어·지원서에서는 영어 학습으로 설명 가능한 상태 유지.
2. **기존 전략 폐기**: "영어로 데려와서 관계로 번다"는 v0.2 가설이 반증됨 — 영어 프레임은 사람을 데려오지도 못했다.
3. **범위 축소**: 첫 버전에서 영어 교정 기능 제거. 검증이 스코프를 *늘리지 않고 줄였다* (시행착오 3번의 반대).
4. **예정 실험 취소**: A가 싸게 데려오고 B가 전환시킨다는 전제의 셀 C 실험을 전제 붕괴로 취소.
5. **부수 발견 — 모달 병목**: 다운로드 클릭 36명 → 이메일 6명(16.7%). 이미 의도를 보인 사람의 83%가 새는 지점을 찾음. 프레임과 무관하게 전체에 적용되는 개선점.

### 다음 관문을 미리 정해둠
> **남은 광고비(약 47만원)는 쓰지 않는다.** 계속 쓰는지 모르는 채 획득에 돈을 쓰는 건 구멍 난 양동이에 물 붓기.

```
검증된 것      ① 반응한다(CTR)  ② 써보고 싶어한다(다운로드 클릭)  ③ 관계로 원한다
모르는 것      ④ 계속 쓰는가(D7)  ⑤ 돈을 내는가
```

다음 단계: 웹앱(PWA) 1~2주 → 사전예약자 6명 투입 → **D7 잔존율 측정** → 판정.

| D7 | 판정 |
|---|---|
| > 50% | 네이티브 앱 착수 + 광고 재개 |
| 30~50% | 첫 5분 온보딩만 재설계 후 재측정 |
| < 30% | 구조 자체를 재검토 |

**판정 기준을 결과를 보기 전에 정했다**는 것이 핵심 — 시행착오 5번(진단 없이 처방)과 선톡 2배를 성과로 쓰지 않은 판단([[projects/company/선톡전송시스템]])의 연장선.

### 검증 설계에서 드러난 판단들
- **봇이 아니라 웹앱으로 검증**: 디스코드/카톡 봇은 감정 선택지·사진·알림 같은 핵심 UX를 재현 못 해 D7이 실제보다 낮게 나온다 — *검증 도구가 검증을 왜곡하지 않게* 고른다.
- **검증 단계는 외부 API, 자체 GPU 서빙은 유저 확보 후**: 원가 구조(월 48만원 고정비, 손익분기 유료 27명)는 계산해두되, GPU 구축에 시간을 쓰면 D7 검증이 밀린다. LLM 호출은 교체 가능한 인터페이스로 분리. → [[skills/working-style]] 서버리스 우선(검증 안 된 가설에 고정비를 묶지 않는다)과 같은 논리.
- **하방부터 계산**: 최악의 손실 2~3개월 + 수백만원, 3개월 안에 답이 나오는 방식이어야 한다는 조건을 먼저 세움. → [[reflections/비용을-줄이는-사람]]의 "절감 = 검증 기회"와 같은 뿌리.

## 확장 — 결과를 먼저 팔고, 바이브코딩으로 구현한다

> **앞으로 가장 필요한 역량으로 보는 방향**: 고객이 돈을 낼 만큼 중요한 문제를 발견하고, 해결할 결과를 먼저 제안하고, AI로 빠르게 구현해 실제 성과로 증명하는 능력.

아래 당근알바 사례는 [원본 영상](https://www.youtube.com/watch?v=0cYwNGATD7U)에 대해 본인이 제공한 리포트(`raw/당근알바-B2B-바이브코딩-영상리포트.md`)에 근거한다. 영상 원문은 직접 확인하지 못했으며, 외부 사례를 본인의 수행 경험으로 사용하지 않는다. 실행 원칙은 사례를 바탕으로 한 해석이다.

### 왜 이 발표가 인상 깊었나 (본인 구술 2026-10-11)

> 코드 한 줄 치는 건 매우 쉬워졌지만, **코드를 치기 전에 확신이 들게 만드는 것**이 어렵다. 고객이 원하지도 않는 제품을 만든 경험이 너무 많아서, 실패를 줄이는 방법으로 이 발표가 정말 인상 깊었다.

[[reflections/초기-스타트업-시행착오]] 1번(잘 만들었는데 아무도 원하지 않았다)과 같은 통증이다. 클로이가 그 통증에 대한 *개인 단위* 답(광고로 먼저 판다)이었다면, 당근알바는 *B2B 신사업 단위* 답 — 확신은 기획서가 아니라 **고객 옆에서 업무를 직접 해보는 과정**에서 만들어진다 — 을 보여준다. 바이브코딩으로 만드는 비용이 0에 가까워질수록 병목은 "만들 수 있는가"에서 "만들어도 되는가"로 옮겨간다는 [[reflections/80퍼센트-프로토타입]] 그림자 2번의 문제의식과도 맞닿는다.

### 광고 검증에서 고객 업무 검증으로

클로이는 제품 없이 반응·사용 의도·판매 문구를 확인한 사례다. B2B에서는 제품을 완성하기 전에 고객의 실제 업무를 작은 서비스로 대신 수행하며 가치를 확인하는 경로가 생긴다.

‘만들기 전에 판다’는 없는 기능을 있다고 설명하는 일이 아니다. **제공할 결과, 범위, 기간, 가격과 현재의 제공 방식을 명확히 합의하는 것**이다. 초기 상품은 완성된 소프트웨어보다 수동 운영을 포함한 문제 해결 서비스일 수 있다.

예를 들어 ‘지원자 관리 플랫폼’ 전체보다 ‘한 지점에서 지원 후 연락 단계의 이탈을 줄이는 파일럿’이 구체적인 제안이다. 고객은 업무 개선을 구매하고, 만드는 사람은 어떤 기능이 필요한지 실제 운영으로 배운다.

### 당근알바 B2B의 출발점 — 동네 알바에서 기업 채용으로

당근알바는 소상공인 중심으로 성장했다. 그러나 채용 시장에는 대규모 상시 채용이 필요한 기업 고객이 있었고, 팀은 B2B 진출을 결정했다. 두 고객은 전혀 달랐다.

| | 소상공인 | 기업 고객 |
|---|---|---|
| 채용 빈도 | 3개월에 한 번 | 대규모 상시 채용 |
| 필요한 제품 | 모바일로 충분 | 지원자 관리 시스템 같은 고도화된 PC 제품 |

일반적인 B2B 개발은 **탑다운** — 핵심 구조를 먼저 잡고 초기 제품을 만들어 고객에게 가져간다. 당근알바 팀은 정반대인 **바텀업**을 택했다: **제품 없이 고객을 먼저 확보하고, 그들에게 필요한 것을 하나씩 만들었다.** 피처와 메뉴가 고객 요청 단위로 쌓여 B2B 사이트가 완성됐다. 고객과 시장을 이해하는 가장 좋은 방법이 제품 없이 고객을 먼저 만나는 것이었다는 게 발표의 결론이다.

### 당근알바 사례에서 읽은 순서

| 출발점 | 먼저 제공한 것 | 배운 것·다음 단계 |
|---|---|---|
| 첫 고객사: 지점별 현황·사용 내역·광고 성과 대시보드 요청 | 제품이 없어 매주 직접 데이터를 뽑아 메일 리포트 | 실제 필요는 **상부 보고용 월간 자료**. 고객이 보는 지표와 확인 주기를 파악. 고객 프로세스를 직접 경험하는 방법이기도 했음 |
| 본사→지점 캐시 배분 시스템 요청 | 제품화하면 결제·계정·광고 시스템으로 수개월짜리 일 → **당일** 구글 시트 장부·슬랙 알림·운영자 수동 지급 | 고객은 내부 구조보다 "지점에 캐시가 지급된다"는 결과를 중시. 고객사별 시트로 운영하다 **사용 고객사가 쌓인 뒤** 정식 제품화 → 이미 쓰는 고객이 있어 제품 개발 협업도 쉬웠음 |
| 물류센터 채용: 지원자는 많은데 출근율이 낮음 (고객 요청이 아니라 팀이 발견) | 지원→연락→채용 확정→출근 4단계를 분석해 **연락 단계 이탈** 발견. 원인은 지원 후 갑자기 요구되는 추가 정보(복잡한 셔틀버스 노선표). 효과·지속 사용이 불확실해 **담당자가 바이브코딩으로 직접** 쉬운 선택 폼 + 지역 필터 셔틀 정류장 탐색 MVP 제작(빌드·배포는 AI에 물어가며, 결과물은 엉성) | 리포트 기준 성과 3배 → 고객사 정식 계약. 검증된 문제를 바탕으로 제품 팀이 확신을 갖고 완성도 높은 제품 개발 |
| 지역별 광고 현황·성과 시각화 요청 | 직접 쿼리 + 시각화 툴로 메일 전달 → 반복 요청에 자체 도구로 자동화 | 여러 고객사 적용 가능성을 보고 고객용 제품 기능으로 제공 |

3배 수치는 지표 정의·표본·비교 조건이 리포트에 없으므로 일반적인 효과 크기나 인과관계로 단정하지 않는다.

**검증의 최소 단위가 팀에서 개인으로.** 기존에는 고객 문제 제기 → PM 설득 → 범위 설정 → 디자인 → 개발 → 전달의 긴 사이클이었고, 설득 자료 준비가 필요했다. 바이브코딩 이후에는 고객과 MVP 검증 → 실제 운영 → 해결 확인의 짧은 사이클로 바뀌었다. 이미 검증된 문제와 해법이라 설득 자료가 필요 없고, 제품 팀 리소스는 확신이 선 곳에만 쓰인다. **고객과 가장 가까운 사람이 직접 만들어 검증한다** — FDE·AI 엔지니어 관점에서 가장 직접적으로 겹치는 지점이다.

**수동 운영은 고객 업무를 배우는 과정이다.** 직접 처리해야 누락 데이터, 승인자, 예외 상황, 실제 보고 주기가 드러난다. [[reflections/확장되지-않는-일을-하는-사람]]의 수작업을 ‘초기 콘텐츠 공급’에서 ‘고객 업무 학습’으로 확장해 볼 수 있다. 바이브코딩은 그 과정에서 발견한 반복 업무를 작동하는 도구로 옮기는 수단이다.

### MVP는 작은 사업 실험

만드는 비용이 낮아져도 검증 질문이 없으면 기능만 늘어난다. MVP의 범위는 기능 개수가 아니라 **이번 실험에서 줄일 불확실성**으로 정한다.

- 문제: 어느 고객의 어느 업무 단계에서 손실이 발생하는가?
- 가설: 어떤 변화가 그 손실을 줄일 것인가?
- 실험: 한 고객·한 지점·제한된 기간에서 무엇을 제공할 것인가?
- 판정: 어떤 지표와 기준으로 계속·수정·중단을 결정할 것인가?
- 사업성: 개선을 경험한 고객이 비용을 지불하고 반복해서 사용하는가?

‘정보 제출을 쉽게 하면 연락 단계 이탈이 줄어드는가?’에 폼 하나로 답할 수 있다면 전체 플랫폼을 먼저 만들 필요가 없다. [[reflections/80퍼센트-프로토타입]]의 정지선도 **가설에 답할 수 있는 최소 범위**로 구체화된다. 성과를 볼 때는 모집 규모·시기·운영 방식의 변화도 함께 확인한다.

고객의 긍정적인 반응, 데이터 제공, 현업 사용, 유료 계약, 재구매는 서로 다른 증거다. B2B에서 결제까지 오래 걸리면 담당자 지정·파일럿 일정 확정·실제 데이터 제공·예산 승인 착수 등 자원 투입을 확인하되, 이를 매출 검증으로 대신하지 않는다. 클로이의 다운로드 클릭도 판매 완료가 아니라 사용 의도의 증거라는 선을 유지한다.

### 커스텀 → 내부 도구 → 공통 제품

B2B에는 "고객 100명을 만족시키려면 제품 100개가 필요하다"는 말이 있을 만큼 요구가 제각각이라, 커스텀은 보통 비용 때문에 피할 대상이다. 당근알바 팀은 바이브코딩으로 만드는 비용이 낮아지자 반대로 갔다: 고객사별로 구조부터 세부 컬럼까지 다른 **커스텀 대시보드를 10개 넘게** 만들었고, 쌓인 화면에서 공통 요구를 찾아 하나의 제품으로 통합했다. 각 대시보드가 하나의 사업 시도였고, **커스텀은 비용이 아니라 고객과 시장을 이해하는 도구이자 공통 제품의 이정표**였다.

발표가 제시한 제품화 단계와 판단 기준:

| 단계 | 기준 | 사례 |
|---|---|---|
| 수동 만족 | 손으로 요청을 채우며 문제 해결 가능성 확인 | 메일 리포트, 구글 시트 캐시 장부 |
| 자체 도구화 | **같은 고객사 안에서** 요청이 반복되면 바이브코딩으로 자동화 | 지역별 광고 시각화 자동화, 셔틀 정류장 좌표 관리 도구(지도 찍고 시트 정리하던 반복 작업 → 엑셀 넣으면 후보 제시 + 버스 정류장 API) |
| 고객사 기능화 | **다른 고객사에서도** 운영 가능하면 고객용 기능으로 제공 | 광고 시각화 기능, AI 폼 빌더(고객 대신 폼을 만들어주다 번거로워 자연어 폼 생성 에이전트를 붙임) |

운영자 본인이 쓸 도구도 같은 방식으로 만들었다: 세일즈 정보·미팅 히스토리를 붙인 메일 작성 크롬 익스텐션(개인용 → 팀 도구), 1회성 리포트 대신 반복 탐색 가능한 시장·잠재고객 분석 유틸리티. **내가 쓸 도구를 직접 만들면 일하는 프로세스가 그대로 제품이 되고**, 검증된 도구는 팀에 남아 위임을 쉽게 한다.

해석하면, 고객별 커스텀 도구는 시장을 배우는 방법이다. 그러나 개발비가 낮아져도 유지보수·권한 관리·데이터 오류·예외 처리 비용은 남는다. 제품화할 때는 요청을 모두 합치기보다 **여러 고객에게 반복되는 문제와 업무 흐름**을 고른다. 공통 흐름은 제품으로, 고객별 차이는 설정으로, 드물고 복잡한 요구는 별도 서비스로 남길 수 있다.

**고객의 문제 확인 → 작은 유료 제안 → 수동으로 결과 제공 → 반복 업무를 내부 도구로 구현 → 성과·재구매 확인 → 공통 제품으로 확장.**

구매 판단을 돕는 데모가 먼저 필요하거나 제안이 거절되어 고객군을 바꿀 수도 있다. 핵심은 큰 개발 투자 전에 실제 고객 행동으로 불확실성을 줄이는 것이다.

[[projects/company/운영도구내재화]]와 연결하면, 개인이 만든 도구를 팀의 자산으로 남기는 과정도 중요하다. 사용법·데이터 정의·접근 권한·유지보수 지식이 함께 이전되어야 개인의 속도가 조직의 역량이 된다. 고객용으로 확장할 때는 개인정보·결제 정확성·장애 대응도 제공 가치의 일부다.

### 내가 기르려는 역량

| 역량 | 할 수 있어야 하는 일 |
|---|---|
| 문제 발견 | 기능 요청 뒤의 손실·업무 병목·현재 대안을 확인 |
| 제안과 판매 | 결과·범위·가격·기간을 정하고 실제 구매 의사를 확인 |
| 수동 실행 | 제품 없이도 작은 범위의 가치를 제공하며 업무를 학습 |
| AI 구현 | 검증할 업무를 폼·도구·자동화로 빠르게 구현 |
| 성과 검증 | 사용량뿐 아니라 업무 개선·지불·반복 사용을 측정 |
| 제품화 판단 | 고객별 요구에서 반복되는 문제를 골라 표준화 |

내 경험에는 빠른 구현·내부 도구 제작·광고 반응 검증의 근거가 있다. 그러나 **직접 유료 제안 → 고객 업무 개선 → 재구매 → 공통 제품화**까지 수행한 사례는 이 문서에서 아직 증명되지 않았다. 이 확장은 완료된 경력의 주장이 아니라 앞으로 가장 중요하게 기르려는 역량의 방향이다.

‘만들기 전에 판다’는 사업 가치를 먼저 확인하는 원칙, 바이브코딩은 그 가치를 빠르게 구현하고 검증하는 수단, 수동 운영은 고객 업무를 배우는 연결고리다. [[reflections/코더에서-문제해결사로]]의 전환을 **고객의 문제부터 구매와 운영까지 책임지는 방향**으로 확장한다.

## 정직한 선

- **말할 수 있는 것**: 제품 없이 $20로 판매 문구를 검증했고, 사전 지정 지표에서 유의한 차이를 얻었고, 그 결과로 기획(문구·범위·실험 계획)을 실제로 바꿨다. 다음 관문과 판정 기준을 미리 정했다.
- **말하면 안 되는 것**: "수요 검증 완료", "제품 출시", "D7 확인". 검증된 건 ①~③(반응·의도·프레임)까지다.
- **표본이 작다**: 방문 69 vs 116, 이메일 2 vs 4. 다운로드 클릭률 차이는 유의하지만, 이메일 전환 같은 하위 지표는 판단 근거가 되지 못한다.
- **광고 클릭 ≠ 사용**: 이 카테고리가 죽는 곳은 거의 항상 ④(지속)다. 기획서 스스로 "첫 관문은 통과했고, 진짜 관문은 아직 열지 않았다"고 기록.

## 그림자

1. **검증이 또 하나의 미루기가 될 수 있다.** 기획서의 최대 리스크 R1이 "출시를 안 함"이고, 창업자는 이미 한 번 겪었다. 검증 단계를 계속 쌓기만 하면 완벽주의(시행착오 1·2)가 *검증*이라는 이름으로 돌아온다. → 판정 게이트에 **기한**(웹앱 1~2주, D7 2주)을 붙여둔 이유.
2. **싸게 측정할 수 있는 것만 측정하게 된다.** CTR·클릭률은 광고로 싸게 재지만, 진짜 질문(지속·지불)은 제품이 있어야 잰다. 가짜 문은 *문구와 대상*을 고르는 도구지 *사업성*을 증명하는 도구가 아니다.
3. **아직 한 번 돌렸다.** 사이클 전체(판다 → 만든다 → D7 판정)를 끝까지 돈 사례는 아직 없다. 지금은 "방식을 설계하고 첫 관문을 실행했다"까지.

## 자소서·면접에서 쓰는 법

- **JD에 "Pretotyping / 만들기 전에 판다 / 수요 검증"이 있을 때** 1번 카드로 쓴다.
- 기원을 붙인다: "만들어놓고 아무도 원하지 않았던 경험 때문에 순서를 바꿨다" — 방법론 흉내가 아니라 수업료로 들리게. (→ [[reflections/코더에서-문제해결사로]] 증거 9번)
- **결과로 바뀐 것**(문구 확정·교정 기능 제거·광고비 보류)을 반드시 같이 말한다. 검증을 했다는 것보다 **검증이 결정을 바꿨다**는 것이 요점.
- 면접 대비: 광고비 $20.19, 표본(방문 69 vs 116), 사전 지정 지표, p ≈ 0.002, 모달 이탈 83%, D7 판정 기준 세 구간을 답할 수 있게.
- 상태를 정확히: "기획과 광고 검증까지 했고, 다음 관문으로 D7을 정해뒀다" — 개발·출시한 것처럼 말하지 않는다.
