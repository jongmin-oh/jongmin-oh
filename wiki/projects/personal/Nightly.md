# Nightly — LangGraph 기반 페르소나 대화 에이전트

**성격**: 1인 개발 · 별도 저장소(`nightly/`) · 진행 중
**기간**: 2026.08.09 – 현재 (커밋 67건)
**형태**: 텔레그램으로 특정 페르소나(강도현)와 대화하는 봇

## 한 줄

캐릭터 챗봇을 다시, 이번엔 **에이전트 프레임워크와 지식 그래프 위에서** 만들어보는 프로젝트.
[[projects/company/캐릭터챗봇API]]에서 직접 오케스트레이션으로 풀었던 문제들(기억·검색·페르소나 일관성)을 LangGraph·Neo4j·Langfuse 같은 표준 도구로 다시 푼다.

## 아키텍처

```
텔레그램 웹훅 → Lambda(FastAPI + Mangum) → LangGraph → OpenRouter(Gemma)
                                              ↕
                            DynamoDB(대화 로그 · 상대 상태) / Neo4j(지식 그래프)
```

**LangGraph StateGraph 5노드**

```
START → build_context → call_model ⇄ tools(get_weather)
                            ↓ (tools_condition)
                        save_reply → [4턴마다] extract_state → END
```

- `tools_condition` / `ToolNode` 로 도구 호출 분기, `add_messages` 리듀서로 메시지 상태 관리
- `save_reply` 뒤 조건부 엣지(`due`)로 4턴에 한 번만 상태 추출 노드로 보냄

## 핵심 설계 결정

### 1. 검색 에이전트를 페르소나 모델에서 분리 (ReAct 서브에이전트)

지식 그래프 검색을 **별도의 빠른 모델이 ReAct 루프로 수행**하고, 페르소나 모델은 그 결과만 받는다.

| 이유 | 내용 |
|------|------|
| 말투 오염 방지 | 페르소나 모델이 직접 검색하면 도구 호출 흔적이 캐릭터 말투를 흐린다 |
| 프롬프트 캐시 보존 | 고정부(페르소나)가 앞에 그대로 남아 prefix 캐시가 유지된다 |
| 레이턴시 | 메신저 대화라 체감이 커서 ReAct 왕복을 `MAX_STEPS = 4`로 제한 |

에이전트는 `open_topic`(주제 내부를 펼침) / `follow_topic`(그 주제를 언급하는 바깥 사실을 모음) 두 도구로 캐다가, 충분해지면 **쓸 사실의 id만** 출력하고 끝낸다.

### 2. 통짜 문서가 아니라 Fact 단위 검색

이전 버전은 주제를 고르면 본문 1,900자가 통으로 딸려왔다. 지금은 문서를 **Topic ← Fact** 2계층으로 쪼개, 에이전트가 낱개 사실 중 쓸 것만 지목한다 (Fact 길이 중앙값 43자, 최대 8개 ≈ 350자).

### 3. 할루시네이션은 사실 부족에서 온다 — 하한선을 둔다

에이전트가 사실을 한두 개만 골라놓고 "충분하다"고 하는 버릇이 있었고, **근거가 얇으면 모델이 빈칸을 지어냈다** (축가 얘기 한 줄에 없는 '형수님'을 만들어낸 사례). `MIN_FACTS = 5` 하한을 두고, 모자라면 같은 주제의 이웃 사실로 채운다(`_pad`).

> 검색 품질 문제를 "더 정확히 찾기"가 아니라 **"근거를 넉넉히 주기"**로 뒤집어 푼 결정.

### 4. 상대에 대해 아는 것 — 50개 필드 상태 스키마

대화 창(최근 20건) 밖으로 밀려나도 남아야 할 정보를 `user_states` 테이블에 따로 모은다.

- 8개 카테고리(금기·기본·일·생활리듬·성향·취향 …) 50개 필드
- **4턴에 한 번만** 추출 — 매 턴 돌리면 잡담 턴이 훨씬 많아 대부분 `{}` 를 받는다
- 페르소나 모델이 아닌 **추출 전용 모델** 사용 (말투를 낼 일이 없으므로)
- 값을 enum으로 정규화하지 않고 전부 문자열로 둠 — `"3교대, 나이트 주엔 낮에 잠"` 이 `{shift_work: true}` 보다 프롬프트에서 낫고 매핑 로직도 안 붙는다
- 빈 필드를 다음 질문거리로 활용 (대화가 멎으면 안 채워진 필드를 묻는다)

### 5. 프롬프트 캐시를 전제로 한 프롬프트 레이아웃

`CORE_PROMPT`(정체성·상황·형식·태도·페르소나) 고정부를 **맨 앞**에 두고, 턴마다 자라는 상대 상태와 매번 달라지는 검색 결과를 뒤에 붙인다. prefix 기반 캐시라 순서를 뒤집으면 매 턴 캐시가 깨진다.

### 6. 서버리스에서만 생기는 문제들을 직접 해결

| 문제 | 원인 | 해결 |
|------|------|------|
| 턴 수를 셀 수 없음 | Lambda는 호출마다 죽어 프로세스가 카운트를 못 가짐 | DynamoDB `ADD` 원자 카운터(`bump_turn`), `ALL_NEW`로 상태까지 한 번에 받아 GetItem 절약 |
| Langfuse 스팬 유실 | 람다가 응답 직후 얼어붙어 백그라운드 배치 전송이 안 나감 | 턴 종료 시 `langfuse.flush()` 강제 |
| 텔레그램 재전송 | 2xx를 받을 때까지 같은 update 재전송 | `last_update_id` 조건부 업데이트로 멱등 처리(`seen`) |
| 메시지 정렬·유실 | 무작위 ID면 "최근 N건" 질의가 성립 안 함 / 키 충돌 시 덮어쓰기 | `[48비트 ms][12비트 카운터][20비트 난수]` base32hex 16자 ID — 사전순 = 시간순, NTP 역행 방어까지 |

### 7. 도구는 "지어내지 않게" 하려고 붙였다

`get_weather` — 날씨 얘기가 나오면 모델이 지어내지 못하게 Open-Meteo를 친다. 한글 지명 지오코딩이 엉뚱한 좌표를 주는 문제(부산 → 36.38)를 확인하고 12개 도시 좌표를 직접 박아둠.

## 지식 그래프 파이프라인 (`knowledge/graph_ingest.py`)

Obsidian 스타일 마크다운 위키(현재 30문서, Person/Trait/Place/Org/Event) → Neo4j 적재.

- 불릿·표행·문단을 각각 하나의 `Fact`로 분해, id는 `문서명#인덱스`로 **재빌드해도 안정**
- `[[위키링크]]` → `언급` 엣지, 프런트매터 `rels:` → 의미 관계 엣지(화이트리스트 22종, 밖이면 빌드 중단)
- 별칭(`aliases`)·검색 힌트(`triggers`)로 카탈로그 구성 — 이름만으론 "대학" → 학창시절이 안 걸려서 손으로 힌트를 붙임
- **셀프체크**: 문서 수 = Topic 수, 미아 Fact 없음, 그리고 **모든 Topic이 허브에서 3홉 내 도달 가능**한지 검증 — 못 닿으면 검색이 영원히 도달 못 하는 섬이 된다
- 전체 삭제 후 재적재 (550노드 규모라 통째로 다시 넣는 게 제일 싸다)
