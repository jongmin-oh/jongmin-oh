# 선톡 전송 시스템

**소속**: [[entities/companies/레플리\|Reppley]]

## 문제

사용자가 챗봇과 대화 후 시간이 지나면 자연스럽게 이탈. "내가 말 걸 때만 응답하는 관계"로는 유대·몰입에 한계. → **캐릭터가 먼저 말 걸어오는 경험**으로 리텐션 향상.

## 기능

| 타입 | 설명 |
|------|------|
| Continue | 이전 대화 맥락을 이어가는 선톡 |
| WakeUp | 새로운 대화를 시작하는 선톡 |

## 아키텍처 결정

**메인 서버에 붙이지 않고 별도 Lambda로 분리.**  
이유: 메인 서버에 추가하면 복잡성 증가. 기존 백엔드 파이프라인(Lambda Step Function 기반 선톡 대상 추출)에 자연스럽게 Lambda를 연결하는 것이 더 깔끔하다고 판단.

```
Lambda Step Function (선톡 대상 추출)
  → SQS (대상 채팅방 목록)
  → Lambda (SAM) — LLM 호출 · 메시지 생성
  → 기존 채팅 발송 시스템 재사용
```

## 한 일

- **시스템 분리** — 별도 Lambda(SAM) + SQS 파이프라인 구축
- **메시지 생성** — 채팅방별 LLM 호출, 캐릭터 페르소나 반영한 선톡 생성
- **대량 처리** — SQS로 LLM 호출·발송 비동기 처리, 동시 호출 폭주 방지
- **프롬프트 개선** — 7일간 실제 생성 결과 **약 5만 건을 직접 검토**하며 반복 개선
- **평가 지표 정의** — 정답이 없는 생성 결과에 평가 기준을 세움 (아래)
- **자동 채점 시스템** — 세운 기준을 자동 채점으로 옮겨 수작업 검수 병목 제거

## 스택

`AWS Lambda (SAM)` · `AWS SQS` · `Python`

## 평가 기준을 어떻게 정의했는가

**문제: 정답이 없다.** 비용 제약으로 경량 모델을 쓸 수밖에 없었고, 5만 건을 직접 읽어도 이 메시지가 좋은지 나쁜지 판단할 기준이 없었다. "캐릭터답다"·"자연스럽다"는 보는 사람마다 잣대가 달라 합의가 안 됐다.

**해법: 기능의 본질적 목표로 되돌아갔다.** 선톡의 존재 이유는 잘 쓴 문장이 아니라 **리텐션 상승**이다. 여기서 측정 가능한 단일 지표로 **푸시 메시지 클릭률**을 정의했다.

**적용:** 페르소나 일관성·문장 완성도 같은 부가 목표보다 클릭률을 우선하도록 **프롬프트 지침을 다시 썼다.** 이후 이 기준을 자동 채점 시스템으로 옮겨 5만 건 수작업 검수 병목을 없앴다.

> 순서가 핵심 — 모델을 바꾸기 전에 **무엇이 '좋은 결과'인지부터 정의**했다. 같은 패턴이 이후 [[projects/company/캐릭터챗봇API|캐릭터 챗봇 API]]의 프롬프트 A/B 테스트(핵심 지표: 대화 지속 턴 수)로 이어진다.

## 결과

- 일평균 **8,000건** 발송 안정 운영
- 평가 지표를 푸시 메시지 클릭률로 단일화, 자동 채점으로 검수 자동화
- ⚠️ 클릭률 개선 폭의 구체 수치는 미기록 `[수치 확인 필요]`

## 아쉬운 점 — 배치 추론을 못 썼다

당시 제약은 **비용**이었고, 그래서 경량 모델을 택했다. 하지만 선톡은 실시간 응답이 아니라 **발송 대상을 미리 뽑아 예약 발송하는 비동기 작업**이다. 즉 지연을 감내할 수 있는 워크로드였다.

> 시간이 더 있었다면 **Gemini Batch API** 같은 배치 추론(동일 모델 대비 약 50% 단가)을 붙여, **같은 비용으로 더 상위 모델**을 써서 선톡 품질 자체를 끌어올릴 수 있었다.

**놓친 지점**: "비용이 부족하다 → 싼 모델을 쓴다"로 바로 간 것. 실제 선택지는 **모델 등급**만이 아니라 **추론 방식(실시간 vs 배치)** 에도 있었다. 워크로드의 지연 허용치를 먼저 따졌다면 트레이드오프의 축이 하나 더 보였을 것이다.

품질 저하를 위의 평가 지표 정의로 우회한 것은 당시 최선이었지만, 애초에 품질을 덜 포기할 길이 있었다.
